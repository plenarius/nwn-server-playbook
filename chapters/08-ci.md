# Chapter 8. CI and runners

**Status:** tiers 2 and 3 are written and tested. Tier 1 is covered by chapter 6: its compile check is the only CI
tier 1 needs.

"CI" (continuous integration) is the habit of having a machine check every change before it is merged. A
**runner** is the machine that does it. GitHub lends you one for each job, fresh every time, and that is all tier 2
uses. Tier 3 adds runners of your own.

## Tier 1

Nothing to do here. Chapter 6's step 8 already gives you a compile check on GitHub's machines, on every pull
request, with no secrets. Come back when you add the tests in chapter 6's tier 2.

## Tier 2. GitHub's machines, with Docker

### What you learn

What a GitHub-hosted runner is, how a whole game server and its database run inside one for a few seconds, what is
worth caching between runs and what isn't, how to give a workflow one secret without giving it to every branch, and
what to do on the day a run fails once and passes the next time.

When you're done, you'll have:

- a picture of the machine your tests run on, and what it costs you;
- a measured answer to "should I cache this?";
- the staging key in a GitHub **environment** that only release tags can reach;
- a calm routine for a flaky run.

This chapter explains the workflows chapter 6 sets up; it adds no new files of its own. **Time:** half an hour of
reading and trying.

### What Layonara does

- **We started on GitHub's machines,** and our compile check still runs there whenever we switch our own runners
  off. Every one of our workflows picks its runner from one repository setting; delete it, and every job goes back
  to GitHub's machines.
- **We moved because of minutes, not speed.** In one week of November 2026 our jobs used 2,450 of the 3,000 minutes
  a month our plan includes, mostly sitting and waiting on a remote machine. Self-hosted runners are tier 3, and
  I'd only move once the minutes, or the size of your content, push you.
- **The test server is the real one, sealed.** Same image as live, a database in memory, a network with no route
  out. That holds on any runner.
- **The tools are pinned.** Every workflow names its versions of nasher, the compiler and the NWNX image, so a run
  today and a run next month build the same thing.
- **Flaky tests are caught, not hidden.** A test that fails is run once more on a fresh server. If it passes then,
  the run still says so loudly, the test is written down as flaky, and someone makes it reliable.

#### 1. GENERIC. Know the machine

Each job gets a fresh virtual machine that is thrown away afterwards. Nothing is left from the last run unless you
ask for it (step 3). On the test, for a private repository, `ubuntu-latest` was:

| | |
|---|---|
| System | Ubuntu 26.04.1 |
| Cores, memory | 2 cores, 7 GB |
| Free disk | about 14 GB of 72 GB |
| Docker, Compose | 29.4.2, 5.1.3 |

Public repositories get bigger machines. Either way, the test server from chapter 6 needs well under one core and
1 GB, so there is plenty of room.

**Minutes.** Public repositories run free. Private ones get a monthly allowance that depends on your GitHub plan
(on your account's **Settings**, **Billing**); past it, jobs stop or cost money, depending on your spending limit.
Our two example workflows used about a minute each per push. A small team with a few pull requests a day stays
far inside the smallest allowance.

#### 2. GENERIC. A game server inside a job

The test step is one line, `tests/run.sh`, the same command as at home. Docker on the runner starts the NWNX image
and MariaDB from `tests/compose.yaml`, on a network of their own with no route out and no ports published. The
whole server lives and dies inside the job: 16 seconds on the test.

Three things in `tests.yml` keep it safe and cheap:

- `timeout-minutes: 20` on the job. GitHub's own limit is six hours, and a hung server would happily use all of
  them. `run.sh` has its own limit too: it gives up after ten minutes.
- `concurrency` with `cancel-in-progress`. Push twice to one pull request and the older run is stopped; only the
  newest commit is worth testing.
- `if: always()` on the summary and the upload. The logs are kept especially when a test failed, because that is
  when you want them.

And one thing worth copying into any workflow of your own: a step that pipes its output (`run.sh | tee file`)
needs `set -o pipefail` first. Without it, the step takes the last command's exit status, `tee`'s, and a failed
test passes. Chapter 6's lessons have the story.

#### 3. GENERIC. Cache what's slow to make, not what's quick to fetch

GitHub can keep files between runs if you ask (the `actions/cache` step): you give the files a **key**, and a
later run that asks for the same key gets them back. Put the version numbers of what you cache in the key, and a
new version simply makes a new cache; you never have to empty one by hand. GitHub drops a cache nobody used for
seven days, and keeps up to 10 GB per repository.

It sounds like free speed, so I measured it on the test's runner before keeping it:

| | Fetched fresh | From GitHub's cache |
|---|---|---|
| nasher and the compiler (83 MB) | 4 s, from GitHub's release pages | 5 s |
| The NWNX image and MariaDB | 19 s, from Docker Hub | 28 s (5 to restore, 23 to load) |

Neither paid, so the template doesn't cache them. GitHub's machines sit next to GitHub's downloads and close to
Docker Hub, and a cache is only one more download. A cache earns its place for something that takes minutes to
*make*, or that comes from far away, rather than seconds from next door: compiled models (chapter 7), a large
module's converted files, a dependency you build from source. When you have one of those, measure both ways, as
above, and keep whichever is faster.

One thing the template does cache: **your haks and talk table** (chapter 6, step 16). They come from your own
download address, a small server of yours, not from next door, and a real server's content is gigabytes, not the
example's 233 bytes. With the example, both ways took about two seconds, so the cache bought nothing in time; it is
there so a hundred test runs don't download your content a hundred times from the machine your players download
from. The key is the version's name, which is the checksum of its list of files, so a new version makes a new cache
and an old one is never wrong. Two things I learned on the test:

- **The cache is saved straight after the download,** with `actions/cache/save`, not at the end of the job. The
  usual `actions/cache` step saves only when the whole job passed, so a failing test would download it all again
  next time, which is exactly when you run again.
- **A cache made on a pull request stays with that pull request.** GitHub lets a branch read its own caches and
  those of the default branch, never another branch's. A release tag after the merge downloaded the version once
  more, although the pull request had cached it; from then on `main`'s copy serves everyone.

The download address has to answer even when the content is cached: the run asks it which version to use. If it's
down, the run stops at its first content step with `could not read https://nwsync.example.org/staging/latest
(HTTP 503): is the download address up?`, which is the right moment to look at chapter 7's step 17.

#### 4. GENERIC. Secrets in an environment

The release workflow needs one secret: the key that can put a module on staging (chapter 6, step 19). Where it
lives matters as much as how it's made.

A **repository secret** is handed to every workflow on every branch. Anyone who can push a branch could write a
workflow that prints it. An **environment secret** is handed only to a job that names the environment
(`environment: staging` in `release.yml`), and only if the environment's rules allow it. Chapter 6's step 20 gave
`staging` one rule: only tags named `v*`. On the test, a job on an ordinary branch that named `staging` never
started:

```
Branch "probe" is not allowed to deploy to staging due to environment protection rules.
```

and the job on a release tag got the key and staged. Pull requests from someone else's copy of your repository (a
fork) get no secrets at all, which is GitHub's rule, not ours.

So a stolen secret is the last line, not the first: the key in the environment can run `stage.sh` and nothing
else, only a tag can reach it, and only staging is behind it. The live game is restarted by a person, never by
GitHub.

Two more habits:

- **Not everything is a secret.** The game host's address and its host key are variables: visible, easy to check,
  and nobody gains anything by reading them.
- **When someone leaves, or a key might have leaked,** make a new key (chapter 6, step 19), replace the secret, and
  delete the old line from `~/.ssh/authorized_keys` on the game host. Ten minutes, and nothing else changes.

On GitHub's paid plans an environment can also require a named person to approve each job before it runs. Our
release doesn't need it, since staging is the whole point of the job, but if you ever give a workflow a key to
something that matters more, that is the setting to reach for.

#### 5. GENERIC. When a run is flaky

A **flaky** test fails sometimes and passes other times, with no change in between. Each failure looks like a real
one, and each "just run it again" teaches the team to ignore red. Here's what I do:

1. **Read before you rerun.** Download `test-logs-lane-1` from the failed run's page and look at the test's lines in
   `logs/nwserverLog1.txt` and any script error in `logs/nwengineLog.txt`. The failed assert's own words usually
   say what was different.
2. **Rerun once, on purpose.** **Re-run failed jobs** on the run's page. If it passes, you have learned that the
   test is flaky, not that it is fine. Say so in the pull request.
3. **Make it fail at home.** Run just that test in a loop until it fails:

   ```sh
   tests/run.sh --filter t_flaky_ > /dev/null
   for i in $(seq 20); do tests/run.sh --no-build --filter t_flaky_ > /dev/null || { echo "failed on run $i"; break; }; done
   ```

   With a test that went wrong one time in three, this said `failed on run 3`, with that run's logs in
   `tests/.run/` to read. Each run is about twelve seconds, so twenty runs fit in a cup of tea.
4. **Fix the test, not the runner.** Most of the flaky tests we've had waited a fixed time for something the
   game does later. After a `DelayCommand(1.0, ...)` in the code, a check at 1.1 seconds will one day run first.
   Check again every quarter second until the thing has happened, with a limit, and use `Test_Async` so the runner
   waits.
5. **Don't switch the test off quietly.** If you can't fix it today, `Test_Skip("flaky: see issue 12")` with an
   issue number keeps it visible.

What I would not do in tier 2 is make the workflow retry failed tests by itself. It hides exactly the thing you
want to see. Our own suite does retry, once, on a fresh server, but it reports every test that needed it; with
five hundred tests on shared machines that is worth the extra machinery. That is a tier 3 subject.

### Lessons

- **What comes from your own server is worth caching.** The tools and images come from next door, quickly, every
  time; your content comes from the small machine your players download from. The one cache the template keeps is
  for that.
- **Measure before you cache.** My first version of the workflows cached the tools, and I nearly cached the
  images too. Measured, the tools came back a second slower than downloading them and the images nine seconds
  slower, so both caches went. A cache helps when making the thing is slow; a download from next door isn't.
- **A pipe can turn a failure green.** `cmd | tee` takes `tee`'s exit status unless the step says
  `set -o pipefail`. This one let a failing test through on the first try.
- **A secret's reach is part of the secret.** The staging key is safe less because of how GitHub stores it than
  because only a tag can reach it and it opens only one door.
- **Always keep the logs.** The run where you need them is the failed one, and a run that passed when it
  shouldn't have is only found by reading them.

environment, and content bigger than the cache's 10 GB per repository (it would simply be downloaded every run).

## Tier 3. Your own runners, and pictures on pull requests

### What you learn

How to run your jobs on a machine of your own instead of GitHub's, safely: each runner good for one job and then
thrown away, in a container, with a Docker of its own for the test server, on your control host or a build
machine, never on the game host, and never for someone else's code. Then two things only your own machine can do:
pictures of the areas a pull request changes, posted on the pull request, and pictures from inside the game itself.

When you're done, you'll have:

- a few runners waiting on your control host (or a build machine), each taking one job and starting again clean;
- every workflow choosing them through one repository variable, and going back to GitHub's machines when you
  delete it;
- three locks against a pull request from a fork reaching them;
- one copy of your haks per version on the machine, shared by every runner;
- chapter 6's test lanes running side by side on that machine, each held to its share of the cores and memory;
- before-and-after pictures of every area a pull request changes, in one comment on it, drawn by nwn-bake;
- in-game stills of a spot, taken by nwn-director with a real game client, when you want to see what a player
  would.

**Time:** about an hour for the runners, half an hour for the pictures, most of it copying your game to the
machine once.

You need chapter 8's tier 2, chapter 6's tier 3 (or at least its tier 2), and the control host from chapter 3.

### What Layonara does

- **We moved for minutes, and stayed for the content.** One week of November 2026 used 2,450 of the 3,000 minutes a
  month our plan includes, mostly jobs waiting on a remote machine. On our own machines the minutes are free, and
  the haks are already there.
- **Four runners on our build machine** (12 cores), in an organisation runner group that only our two private
  content repositories may use. Public repositories never use them. The runners run as a system user with no
  sudo and no Docker, held to 6 GB of memory and kept out of the rest of the system.
- **Every workflow opts in through one repository variable,** and falls back to GitHub's machines when it is
  deleted. It's the first thing we reach for when a runner misbehaves.
- **The tests run beside the runners, not in them.** A runner only holds an SSH session; the suite runs as another
  user with rootless Docker, in three lanes of 4 cores and 4 GB each, the whole user capped at 8 of the 12 cores, so
  the rest of the machine never waits for a test.
- **Haks for the tests** are a dated copy of what our build publishes, refreshed when a build finishes, and each run
  takes its own snapshot of it, so a build finishing half-way through a run can't change the haks under a test.
- **Pictures on every pull request.** nwn-bake draws, before and after, the areas, creatures, items and placeables
  a pull request changes: an area as a close-up of each changed spot with coloured rings, and an overview. They
  sit on a branch of their own, in one comment, at most 30, and the job never fails a pull request.
- **nwn-director** films spots and takes stills with a real game client. It runs on demand on a machine with a
  game client and a CD key of its own, not in our CI.

The design below is simpler than ours on purpose: a runner and its Docker in containers, thrown away after each
job. Ours grew over a year and is a better fit for one big machine; this one is easier to set up from nothing and
gives every job a clean start, as GitHub's machines do.

### The human playbook

The files are in [`templates/runner`](../templates/runner): the runner image (`Dockerfile`), the hook that refuses
forks (`hooks/job-started.sh`), the supervisor (`runners.sh`), its settings (`runners.conf.example`) and its
service (`nwn-runners.service`). In the module repository: `.github/workflows/previews.yml` and `tools/previews.sh`.

#### 7. GENERIC. Decide, and choose the machine

Move to your own runners when GitHub's minutes or your content's size push you, not before. GitHub's machines are
free of upkeep; yours are one more thing to keep updated and safe.

Where they go:

- **Never the game host.** A test run can use every core for minutes; your players would feel it.
- **The control host is fine for a small team,** with the limits in step 10 so a test run can't starve Coolify.
- **A build machine of its own is better** if you can spare a few euros a month: chapter 1's cx33 (4 cores, 8 GB)
  ran three runners comfortably on the test.

Here is the one thing to understand before you start. Each runner has its own Docker, and that Docker runs as
"privileged", which means a job on it could, with some effort, take over the machine. On the control host, that
reaches Coolify, and through Coolify, the game host. That is acceptable only because every job on these runners is
code your own team wrote and merged or pushed to a branch; step 12 makes sure nothing else ever runs there. If
your team includes people you don't know well, use a separate build machine, and treat it as theirs.

#### 8. ADAPT. A token for one repository

Change: the repository's name.

The runners register themselves with GitHub, and for that they need a token. On GitHub, your picture, **Settings**,
**Developer settings**, **Fine-grained tokens**, **Generate new token**:

- **Repository access:** only your module's repository;
- **Permissions:** **Administration**, read and write (that's the permission GitHub asks for to register runners);
- **Expiration:** a year, with a reminder in your calendar a week before.

This token can change the repository's settings, so it is kept like a password. On the machine:

```sh
sudo install -d -m 700 /etc/nwn-runners
sudo sh -c 'umask 077; cat > /etc/nwn-runners/token'     # paste the token, Enter, then Ctrl-D
```

It never reaches a job. For each runner, `runners.sh` asks GitHub for a one-time registration (a
"just-in-time configuration"), good for one runner and one job, and only that goes into the runner's container.

If your repositories belong to an organisation, the same works with an organisation token and a **runner group**
that names which repositories may use the runners; ours is set up that way.

#### 9. GENERIC. The runner image

On the machine, with this repository's `templates/runner` copied to `~/runner`:

```sh
sudo apt-get install -y jq
cd ~/runner && sudo docker build -t nwn-runner:2.338.2 .
```

It's GitHub's own runner image, version 2.338.2, plus the two tools the module's workflows use and it lacks (the
GitHub CLI and Docker Compose, each pinned and checked against its checksum), minus the runner user's `sudo`. And
one file: `hooks/job-started.sh`, which the runner runs before every job (step 12).

#### 10. ADAPT. Start the runners

Change: `REPO`, and the limits for your machine.

```sh
sudo cp ~/runner/runners.conf.example /etc/nwn-runners/runners.conf
sudo nano /etc/nwn-runners/runners.conf        # REPO=you/mymodule; SLOTS, CPUS, MEMORY: below
sudo install -m 755 ~/runner/runners.sh /usr/local/sbin/
sudo cp ~/runner/nwn-runners.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now nwn-runners
sudo runners.sh status
```

```
slot 1: Up 12 seconds
slot 2: Up 12 seconds
slot 3: Up 12 seconds
mymachine-1-1795716263 online busy=false nwn,self-hosted,linux,x64
mymachine-2-1795716263 online busy=false nwn,self-hosted,linux,x64
mymachine-3-1795716263 online busy=false nwn,self-hosted,linux,x64
```

Each **slot** is one runner waiting for one job. When the job is done, the runner, its Docker and the job's files
are thrown away and the slot starts again: on the test, five or six seconds from one job's end to the next runner
waiting. What a slot keeps between jobs is its Docker's downloaded images, so the NWNX image isn't fetched for every
job.

The limits: `CPUS` and `MEMORY` hold each slot's Docker, where the test server and its database run. `SLOTS` times
those is what a full set of lanes can take. On the test's 4 cores and 8 GB, with three slots of 1.5 cores and 3 GB,
a full run of three lanes took the machine from 0.9 GB of memory in use to 2.2 GB at most, with all four cores busy
for a few seconds at a time and a load average of about 1.

`sudo journalctl -u nwn-runners -f` shows each runner waiting and finishing, with the job's result:

```
slot 2: runner mymachine-2-1795716093 finished: Job plan completed with result: Succeeded
```

#### 11. GENERIC. Send the jobs there

In the module repository's **Settings**, **Secrets and variables**, **Actions**, **Variables**, add `CI_RUNNER`:

```
["self-hosted","nwn"]
```

Every workflow of the template reads it: the compile check, the tests, the release, the flake report and the
pictures. From the next push, their jobs run on your machine. To go back to GitHub's machines, at any time, for any
reason, delete the variable. Nothing else changes, and the next run goes to GitHub.

On the test, the whole suite in three lanes took 1 minute 22 seconds on the runners the first time (each slot
downloading the images) and 1 minute 7 seconds once they had them, against 1 minute 9 seconds on GitHub's. For
eighteen tests that's no faster, and I didn't expect it to be: the gain is in minutes, which are free here, and in
content, which is next door.

#### 12. GENERIC. Never for a fork

A pull request from someone else's copy of your repository (a fork) runs the workflow as that pull request has
it, so whoever opened it can change what the job does. On your machine that must never happen. Three locks, each
on its own enough for most cases, together as good as it gets:

1. **The repository's own setting.** In a private repository, GitHub doesn't run workflows from forks unless
   you switch it on (**Settings**, **Actions**, **General**, "Fork pull request workflows"): leave it off. In a public
   one, set "Approval for running fork pull request workflows" to **Require approval for all external
   contributors**, and read a pull request before you approve its run.
2. **The workflow sends forks to GitHub's machines.** Every job's `runs-on` in the template says: if this is a
   pull request from another repository, `ubuntu-latest`, whatever `CI_RUNNER` says.
3. **The runner refuses them anyway.** A fork could edit lock 2 away in its own copy of the workflow. So the runner
   itself runs `hooks/job-started.sh` before every job, and it fails the job before its first step when the job
   is from a pull request whose code comes from another repository, from a comment (anyone can write one), or
   from a repository the runner isn't for.

On the test, a job started by a comment reached a runner and stopped there:

```
A job started hook has been configured by the self-hosted runner administrator
refused: jobs started by comments don't run on self-hosted runners
##[error]Process completed with exit code 1.
```

and, given the event of a real pull request from a fork of a public repository, the hook said:

```
refused: a pull request from someone/their-fork, not from you/mymodule itself; self-hosted runners never run code from forks
```

#### 13. GENERIC. The haks, once per machine

On GitHub's machines the tests keep your haks in GitHub's cache (tier 2, step 3). On your own, that would be a
round trip to GitHub and back for files your machine could simply keep. So `runners.sh` gives every runner one
shared folder, `/srv/nwn-runners/cache/nwsync`, and the tests workflow uses it whenever it's there:

- each version of your content gets a folder of its own, named after the version;
- a lane that finds the version missing downloads it into a new folder and moves it into place only when it's
  whole, so a lane never reads half a download, and two lanes downloading at once simply keep one;
- `runners.sh` removes a version nobody has used for 14 days when it starts.

On the test, with a stand-in download address on the same machine, the first lane downloaded the version
(`content a5f67333...: 2 files checked, 1 haks, 1 talk tables`) and the two lanes a few seconds behind it said
`content a5f67333...: already on this machine`. Three downloads started at the same moment, by hand, each finished
and the first to finish was kept; the other two threw theirs away.

#### 14. ADAPT. Lanes on your machine

Change: `SLOTS` and the limits, to your machine.

Chapter 6's lanes need nothing new here: each lane is a job, each job takes a slot, and each slot's Docker is held
to its share. With `TEST_LANES` at 3 and three slots, the three lanes run at once; with two slots, the third waits
for the first free one. The plan job and the final `tests` job take a slot each for a few seconds.

If your control host also runs Coolify and a website, leave them a core: three slots of 1.5 cores on 4 cores is
already more than the machine has, which is fine for short bursts, because each limit is a ceiling, not a
reservation.

#### 15. ADAPT. Pictures of the areas a pull request changes

Change: where your game is.

[nwn-bake](https://github.com/plenarius/nwn-bake) draws an area from its own files, the tiles' models and
textures, without the game running. The workflow `previews.yml` uses it on every pull request that changes an
area: it draws each changed area before (the branch the pull request started from) and after, from the south-west
and from above, and posts one comment with the pictures, edited on every push rather than added to.

It needs the game's models and textures, and those are in your own installed copy of the game, which you bought
and nobody may hand out. So it runs only on your own runners, with your copy on the machine, read-only:

```sh
sudo mkdir -p /srv/nwn-game && sudo chown $USER: /srv/nwn-game
# From your own computer, where the game is installed (Steam's folder shown):
rsync -a --exclude=data/mov --exclude=data/mus --exclude=data/amb \
  ~/.local/share/Steam/steamapps/common/Neverwinter\ Nights/{data,lang} you@MACHINE:/srv/nwn-game/
```

About 5 GB without the movies and music; on the test it took 23 minutes over a home connection. Then in
`/etc/nwn-runners/runners.conf`:

```
GAME_DIR=/srv/nwn-game
```

and `sudo systemctl restart nwn-runners`. Every runner now sees the game at `NWN_GAME_DIR`. Copy
`previews.yml` and `tools/previews.sh` from the template into your repository. On the test, a pull request that
changed two tiles of an area got its comment about a minute after it was opened: a table, one row for each view,
with the area before on the left and after on the right, the missing tile and the turned one plain to see.

```
### Pictures of the changed areas

| Area      | Before                    | After                    |
|-----------|---------------------------|--------------------------|
| start sw  | (picture from the south-west, before) | (the same, after) |
| start top | (picture from above, before)          | (the same, after) |
```

What to know:

- **Drawing is quick.** One small area, both views, before and after, took under a second. A big area takes a few
  seconds; nwn-bake can draw close-ups of just the changed spots (`--region` and `--mark`), which is what we do
  for big areas.
- **The pictures live on a branch called `previews`,** in a folder per pull request and commit, never in your
  history. When the pull request is closed, the `forget` job takes its folder off again.
- **It never fails a pull request.** No game on the runner, a draw that fails, too many areas: each gives a line
  in the run's log, not a red cross.
- **Haks.** An area made of a custom tileset needs your haks. Give the job a user folder in `NWN_BAKE_USER` with
  your haks in `hak/` (the content cache from step 13 has them).

#### 16. ADAPT. Stills from inside the game, with nwn-director

Change: your own CD key, your character.

[nwn-director](https://github.com/plenarius/nwn-director) runs your module on a local server, logs a real game
client in as an invisible cameraman, and takes pictures of a spot: what a player standing there sees, lighting,
effects and all. For stills it needs no screen and no graphics card, so it can run on the build machine. It's for
the moments a picture of the area isn't enough: "is the fog in this cave right?", "what does this spot of the bug
report look like?".

It needs a game client, and a client needs a CD key, and that is why I run it by hand, not in a workflow:

- **Use a second CD key,** not the one you play with. A key can be in only one game at a time; nwn-director's
  cameraman can't join while you play on the same key, and the other way round.
- **The key never goes into a repository, a workflow, or a log.** It lives in one file on the machine, readable by
  the user who runs nwn-director only. You type it in once:

  ```sh
  mkdir -p ~/.local/share/Neverwinter\ Nights
  ( umask 077; printf '[NWN1]\nYourKey=%s\n' "$(read -rsp 'CD key: ' k; echo "$k")" > ~/.local/share/Neverwinter\ Nights/cdkey.ini )
  ```

  `read -s` keeps the key off the screen and out of the shell's history.

What else it needs on the machine (the runners don't use any of it):

```sh
sudo apt-get install -y --no-install-recommends xvfb xdotool ffmpeg libgl1 libgl1-mesa-dri libopenal1 x11-utils
git clone https://github.com/plenarius/nwn-director ~/nwn-director
```

plus the neverwinter.nim tools (chapter 6, step 1) on the `PATH`, the game's client program in `/srv/nwn-game/bin`
(copy `bin/linux-x86` beside the data from step 15), and any character of yours in
`~/.local/share/Neverwinter Nights/localvault` to be the cameraman; it's never seen. Then:

```sh
python3 ~/nwn-director/director.py film mymodule.mod --spot start@20,20 --stills 4 \
  --character ~/.local/share/Neverwinter\ Nights/localvault/mychar.bic --game /srv/nwn-game --out ~/stills
```

It writes four pictures turning round the spot, and a contact sheet of them, to `~/stills`. The director's own
README says what to expect on a small machine: eight stills of a town in about three minutes on four busy cores.

I have to be honest about my test here. Everything up to the cameraman's login worked on the test machine: the
module copied with the director's script in it, the server started in Docker, the game client drew its screens on
the CPU in a virtual display from the copied game, and found the server. The login itself was refused, three times
over twenty minutes, with "Your CD Key is still in use, please wait 5 minutes and try again": the spare key I used
was, as far as I can tell, in a game somewhere else at the time. So this step is written from the director's
README and that partial run, not from stills I took. If you see the same message, check nothing else is playing
on that key, wait the five minutes, and run it once more.

#### 17. LAYONARA-ONLY. Our runners

Ours differ from the template in three ways, each from a year of running them. The runners themselves have no
Docker at all: a test job only opens an SSH session to a separate user on the same machine, whose rootless Docker
runs the lanes, so a job can never reach more than that user's own files. Their units have a hardening drop-in
(their own `/tmp`, no access to home folders, a memory cap). And when we hire a big server for an afternoon, it
offers ten more lanes, and the tests use them while it's up.

### The agent playbook

If you work with an AI agent, [`playbooks/08-ci-tier3.md`](../playbooks/08-ci-tier3.md) has these steps in a fixed
shape. It needs a person for the token, the CD key and copying the game; it stops and asks before it sets
`CI_RUNNER`, before it opens a pull request to try the pictures, and before anything changes a repository's fork
settings.

### Lessons

- **A runner registered this way has only the labels you give it.** The first runners I started had the label
  `nwn` and nothing else, and every job that asked for `["self-hosted","nwn"]` sat waiting for a runner that
  would never come. `runners.sh` now adds `self-hosted`, `linux` and `x64` itself.
- **Stop a runner politely.** Removing a waiting runner's container outright left GitHub believing it was online
  for a minute or two, and an offline registration behind for good. `runners.sh` now asks each runner to stop,
  which tells GitHub, and removes what's left of its own runners when the service stops.
- **A loop that restarts things needs to know when to stop.** The first version, told to stop, removed its
  runners, and each slot promptly started a new one on its way out. A small flag file now says "stopping".
- **A restart shouldn't cancel a job.** I restarted the service once while a lane was running, and the lane was
  cancelled, failing the run. Stopping now removes the waiting runners first and lets a running job finish (up to
  20 minutes); the same restart later waited 34 seconds for two lanes, and the run passed.
- **The fork rule belongs on the runner, not only in the workflow.** A pull request runs the workflow as the pull
  request has it, so a rule that lives only in the workflow is a rule the pull request can delete. The hook on
  the runner is the rule; the line in the workflow is a courtesy that keeps forks' jobs from failing there.
